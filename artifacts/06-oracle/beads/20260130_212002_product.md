## 2) What the Flywheel actually is (in one paragraph)

The Flywheel is a **composable CLI toolchain** for running **multiple coding agents in parallel** (typically via tmux + agent CLIs), while keeping them from stepping on each other through **(a) coordination + file reservations**, **(b) graph-based task triage**, **(c) aggressive automated scanning**, and **(d) durable memory/search over past sessions**. Its own docs describe it as “15 core tools and 7 supporting utilities” that reinforce each other. ([Agent Flywheel][2])

---

## 3) The core loop (the thing that makes it “agentic” rather than “multi-chat”)

The Flywheel page states the core loop explicitly:

> **NTM spawns agents → they register with Mail → they use BV to find tasks**
> This is the “agents figure out what to do next” mechanism. ([Agent Flywheel][3])

That’s a very particular design choice: instead of building one mega-agent, it builds a “factory floor” where agents are (ideally) interchangeable workers and the *system* provides the structure.

## 4) Tooling stack, organized by function (best-of synthesis)

### A) Orchestration: spawn and manage the swarm

**NTM (Named Tmux Manager)**
Purpose: treat tmux as the agent cockpit—spawn multiple agents in named panes, broadcast prompts, keep sessions persistent across SSH disconnects. ([Agent Flywheel][3])

Practical effect: you get parallelism without the “which terminal is doing what?” chaos.

---

### B) Coordination: message bus + “don’t edit the same file” leases

**MCP Agent Mail (“Mail”)**
Purpose: a “Gmail-like” coordination layer for agents: threaded messaging + searchable history + **advisory file reservations** (leases) to prevent merge-conflict hell. ([Agent Flywheel][2])

The docs explicitly position it for multi-agent setups where several Claude/Codex/Gemini instances share one repo and need to coordinate ownership. ([Agent Flywheel][2])

---

### C) Task system: turn work into a dependency graph and triage by math

**beads_rust (“BR” / `br`)**
Purpose: local-first issue/task tracking with dependencies (a DAG), designed to live *inside the repo* (under `.beads/`). The Flywheel docs describe the storage approach as “SQLite + JSONL hybrid” with git-friendly export for collaboration. ([Agent Flywheel][2])
It is also described as a Rust port of the “beads” system associated with **Steve Yegge**. ([GitHub][5])

**Beads Viewer (“BV” / `bv`)**
Purpose: compute graph metrics over the Beads dependency DAG so agents work on what unblocks the most progress. The docs list metrics like PageRank, betweenness, critical path, cycles—plus additional ones exposed in robot outputs (HITS, eigenvector, k-core). ([Agent Flywheel][6])

**Robot mode matters**: Flywheel docs explicitly warn: never run bare `bv` in agent contexts (it launches a TUI); use `bv --robot-*`. ([Agent Flywheel][6])

---

### D) Quality gate: fast, noisy scanners that LLMs can stomach

**Ultimate Bug Scanner (“UBS” / `ubs`)**
Purpose: run a broad, pattern-based bug scan before commits; the Flywheel docs call out “1000+ detection rules,” AST-grep patterns, consistent JSON output, and “sub‑5‑second feedback loops.” ([Agent Flywheel][3])

The intended philosophy is pretty explicit: tolerate false positives because agents can evaluate findings without getting demoralized. ([Agent Flywheel][3])

---

### E) Safety: defense-in-depth against catastrophic agent commands

The Flywheel site describes a layered approach:

* **DCG** blocks obvious destructive commands *pre-execution*. ([Agent Flywheel][3])
* **SLB** adds an approval workflow for “risky operations” that need judgment, and the docs describe it as preventing dangerous commands from running without approval. ([Agent Flywheel][3])

This “DCG catches patterns; SLB catches contextual risks” framing is spelled out as defense in depth. ([Agent Flywheel][3])

*(Some of the more detailed claims in your LLM bundle—e.g., risk tiers, bypass env vars, regex limitations—appear plausible, but treat them as “report claims” unless you pin them to specific README lines yourself.)*

---

### F) Memory: searchable history + curated “procedural memory”

**CASS (Coding Agent Session Search)**
Purpose: index and search past agent sessions across many tools; Flywheel docs emphasize sub‑60ms prefix queries and broad connectors (Claude, Codex, Cursor, Gemini, ChatGPT, etc.). ([Agent Flywheel][3])

**CM (CASS Memory)**
Purpose: store distilled learnings as procedural memory (“playbooks”) so future agents don’t repeat mistakes and can retrieve what worked. The Flywheel docs describe CASS+CM together as “collective memory.” ([Agent Flywheel][3])

---

### G) Multi-repo and account logistics (the “fleet” layer)

**RU (Repo Updater)**
Purpose: parallel sync across many repos and “agent-sweep” style automation; Flywheel docs describe coordinated repo claiming (optionally via Mail) to avoid conflicts. ([Agent Flywheel][3])

**CAAM (Coding Agent Account Manager)**
Purpose: manage multiple agent accounts/keys and rotate credentials so NTM can spawn agents with the right credentials. ([Agent Flywheel][3])

## 7) A clean “best-of” mental model you can reuse

If you remember only one thing, make it this:

**This ecosystem treats autonomous coding as a coordination + prioritization + safety + memory problem.**
Not “find the smartest agent,” but “build the factory rails so average agents can run fast without wrecking the place.”

### The five operational phases (practical abstraction)

This is consistent across the various docs and your LLM bundle:

1. **Plan**: represent work as a dependency graph (BR / Beads). ([Agent Flywheel][6])
2. **Prioritize**: compute graph bottlenecks and pick next-best tasks (BV robot triage). ([Agent Flywheel][6])
3. **Execute in parallel**: spawn multiple agents and feed them tasks (NTM). ([Agent Flywheel][3])
4. **Coordinate edits**: reserve files + keep threads of decisions (Agent Mail). ([Agent Flywheel][2])
5. **Gate + remember**: scan before committing (UBS) and store retrievable memory (CASS/CM). ([Agent Flywheel][3])
